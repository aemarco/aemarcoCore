# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

aemarcoCore is a set of .NET 10 NuGet libraries for crawling: people/model info and wallpapers. Three packages plus tests and a Nuke build:

- `aemarco.Crawler` (`aemarcoCrawler`) — shared core: page loading (`IHtmlClient`) and the one rate limiting of all crawler requests, page types (`PageUri`, `PageDocument`, `PageNode`), `CrawlerAttribute`, `SkipTestingAttribute`, `CountryService`, `CrawlerInfo`.
- `aemarco.Crawler.Person` (`aemarcoPersonCrawler`) — `IPersonCrawler` aggregating many site crawlers into a merged `PersonInfo`.
- `aemarco.Crawler.Wallpaper` (`aemarcoWallpaperCrawler`) — wallpaper site crawlers mapped to an internal `Category` enum.

## Conventions

## Commands

Build/test/pack go through Nuke (`build/`), which is also what CI (GitHub Actions, `.github/workflows/build.yml`, hand-written, runs `./build.cmd Publish` and uploads the `drop` and `test-results` artifacts) runs. On GitHub, test results show up as annotations and job summary (`GitHubActionsTestLogger`), and the `Tests` target appends ReportGenerator's `SummaryGithub.md` coverage table to `$GITHUB_STEP_SUMMARY`. The whole test stack (test SDK, adapter, coverlet, the logger, `aemarcoToolboxTesting` which brings NUnit and Shouldly, NSubstitute, DI) is referenced in `Tests/Directory.Build.props`, so a test csproj only holds its project references. The props also declare the global usings for that stack and the common `System` namespaces (`<Using Include=... />`); a test project's `GlobalUsings.cs` holds only its own (`aemarco.Crawler.*`, `System.Reflection`, ...). Keep `coverlet.collector` there in particular: its targets live in `build/` only, so a transitive reference never deploys the collector and coverage comes out empty. There is no `global.json`: the build uses the installed SDK, the workflow sets up `10.x`. The Nuke targets work on the whole solution; to verify a change, build or test only the project at hand (see below), as in the Internals file. A push to `main` publishes: the workflow's `publish` job pushes the `drop` packages to nuget.org (trusted publishing via OIDC, environment `push-to-nuget-org`, secret `NUGET_USER`, `--skip-duplicate`). So pushing to `main` is the deploy here, and the deploy stance of the Internals file applies to it:

```
./build.cmd Compile      # CountryUpdate -> Restore -> Compile
./build.cmd Tests        # + tests with coverage (trx/cobertura in build/output)
./build.cmd Pack         # nupkgs into build/output/drop
```

Plain dotnet works for day-to-day work (the tests use NUnit and Shouldly, as in Internals; an unordered collection compare is `ShouldBe(expected, true)` (`ignoreOrder`), `ShouldBeFalse()`/`ShouldBeInRange` take no nullables, so `bool?` uses `ShouldBe(false)` and `double?` goes through `ShouldNotBeNull()` first):

```
dotnet test Tests/aemarco.CrawlerTests
dotnet test Tests/aemarco.Crawler.PersonTests --filter "FullyQualifiedName~FreeonesTestsWithFoxyDi"
dotnet test --filter "Name=Crawler_Country"
```

Note: the Nuke `CountryUpdate` target **rewrites** `aemarco.Crawler/Resources/CountryRegionData.json` (merges CultureInfo, CountryData.Standard and hardcoded data) on every Nuke build, so expect that file to show up as modified after a build. Versioning is automatic via Nerdbank.GitVersioning (`version.json`, 10.0). The Nuke build reads the version through `[NerdbankGitVersioning]` (logged by `Info`), which needs the `nbgv` tool as `PackageDownload` in `_build.csproj`; the `Nerdbank.GitVersioning` library alone does not feed the attribute. Keep both versions in step.

Projects target `$(DefaultNetVersion)` (`net10.0`) with `Nullable` enabled, both from the root `Directory.Build.props`. `Tests/Directory.Build.props` imports the root one and adds only the test setup (`IsPackable=false`, `IsTestProject`, the test packages). `build/Directory.Build.props` blocks the root import (Nuke) and repeats `DefaultNetVersion`, so a framework bump touches the root and `build/`; the Nuke `_build` project has no `Nullable`. Package versions are managed centrally in `Directory.Packages.props` (CPM, `ManagePackageVersionsCentrally` set in that file so `build/_build.csproj` is covered too, although `build/` blocks the root `Directory.Build.props`). A `PackageReference` never carries a `Version`; `PackageDownload` (ReportGenerator in `_build.csproj`) does, CPM does not manage it. `nuget.config` clears machine-wide sources and uses nuget.org only, like CI.

## Architecture

**Person crawler** (`aemarco.Crawler.Person`)
- Each site is a class in `Crawlers/` deriving `SiteCrawlerBase` (implements internal `ISiteCrawler`). It must carry `[Crawler("Friendly Name", priority)]` — `AddPersonCrawler()` discovers all non-abstract `ISiteCrawler` types by reflection, throws if the attribute is missing, and registers each as a **keyed transient** service by type name. File-name prefix (`12_Freeones`) mirrors the priority; lower value wins on merge.
- Subclasses implement `GetGirlUri(name)` and `HandlePersonEntry(page, token)` (and optionally `HandlePersonNameEntries`), filling the base-class `Result` via helpers (`UpdateName`, `UpdateCountry`, `UpdateMeasurements`, `UpdateSocial`, `UpdateProfilePictures`, ...).
- `PersonCrawler` runs all (optionally filtered via `AddPersonSiteFilter`) crawlers concurrently, collects failures into `PersonInfo.Errors` rather than throwing, then `PersonInfo.Merge`s results. `Crawlers/Obsolete/` holds dead sites kept for reference.

**Loading and rate limiting** (`aemarco.Crawler`, registered once by `AddCoreCrawler()`, whichever package calls it first) — nothing static: every request of every crawler goes through one singleton `CrawlerRateLimiter` (one gate per domain = host without `www.`: it knows the next allowed send, one interval after the last, and requests wait in line for it; deliberately not a token bucket, which only keeps the average rate: its refill timer lets a request through a few ms after the previous one whenever a token sat unused). `RateLimit(Permits, Window, Jitter)`: two sends are never closer than `Window / Permits`; every request first sleeps a random 0..`Jitter` and then takes its turn, so a large jitter does not shorten the gap (a sequential crawler sends `max(interval, jitter + latency)` after the last send); the limits come from the options `CrawlerRateLimits` (`Default` 60/min with 0.5s jitter, `Domains` per domain), which the consumer adjusts with one call of its own, `services.AddCoreCrawler(x => ...)` (the packages call `AddCoreCrawler()` themselves without an action; `Domains` starts with `wallpaperscraft.com` 60/min with 1.5s jitter (the old crawl waited 1-2.5s between its pages), and `wallhaven.cc` 40/min without jitter, headroom under the api's 45). Those are default values of the class, not a `Configure` in `AddCoreCrawler`: every package calls `AddCoreCrawler`, a `Configure` there would be registered again after a consumer's and overwrite it; as class defaults every consumer `Configure` comes after them, whatever the call order. `RateLimitHandler` asks the limiter; any `HttpClient` gets the whole request pipeline with `AddCrawlerPipeline()` (sites and apis alike): `RetryHandler` outside (an attempt that timed out, or a 408/429/5xx, is tried again, waiting for `Retry-After` up to `MaxRetryAfter`, otherwise a doubling backoff), then `RateLimitHandler` (so every attempt takes its turn at the gate), then `AttemptTimeoutHandler` (the time of one network attempt, the wait for the gate is not part of it; a timeout is a `TimeoutException`, never an `OperationCanceledException`, which means the caller cancelled). `HttpClient.Timeout` is infinite for that reason. The numbers are the options `CrawlerRequestOptions` (5 attempts, 30s, 2s backoff, 1 min `MaxRetryAfter`), set with `services.Configure<CrawlerRequestOptions>(...)`; tests set a tiny `Backoff`, or every failing request waits 2+4+8+16s. Crawled sites load through `IHtmlClient` (`Contracts/Clients`, typed `HtmlClient` in `Clients/`): the pipeline, HtmlWeb's old user agent, no cookies, decompression; only success and 404 deliver their page (crawlers recognize not-found pages by content), any other status throws `HttpRequestException` with its `StatusCode`: a 429, 403 or challenge page would parse as "no entries" and read as the end of the pages. Crawlers navigate through their base class (`await Navigate(pageUri)`); `IHtmlClient.Navigate` takes a nullable `PageUri` and returns null for it without a request, so `Navigate(node?.GetHref()) is not { } page` needs no extra check. `PageUri` is data only. Both pipelines are async end to end, nothing blocks on a task (no `GetAwaiter().GetResult()`); the wallpaper offers too (`GetCrawlOffers`, some sites read their categories from their pages), hence `IWallpaperCrawler.GetAvailableCategories()` is async. The clients and handlers await with `ConfigureAwait(false)`.

**Wallpaper crawler** — `WallpaperCrawlerBasis` is what every crawler needs (offers, filters, known urls, `RunOffer`, result, warnings; abstract `GetCrawlOffers` and `HandlePage`). The sites read from html pages derive from `HtmlCrawlerBasis` (it owns `IHtmlClient`/`Navigate`, the page loop with a node per entry, and `GetContentCategory`, which maps site category names to `ContentCategory`: internal `Category` enum plus suggested adult-level range); an api crawler (Wallhaven) derives from the plain base and implements `HandlePage` itself. Both live per site in `Crawlers/`; `AddWallCrawler` registers the concrete (non abstract) subclasses. `AddWallCrawler()` registers every `WallpaperCrawlerBasis` subclass as a **keyed transient** by type name; the key list lives in its own `WallCrawlerRegistry` type, so it does not collide with the person registrations in a shared container. Crawler instances hold the state of one crawl, `WallCrawlerProvider` hands out fresh ones per `CrawlWallpapers`. Paging comes with `Start`, not the constructor (`FirstPageOnly` for sites that only ever crawl page 1). Each site × internal category is a crawl row in aemarcoInternals, so changing which crawlers are found or their friendly names adds or drops rows there. **The offer is the unit of a crawl** (`CrawlOffer` holds its new/known entries and albums and the urls it found): entries come newest first, and a consumer stops at ten known entries in a row, so entries delivered from pages before a failure would hide the missed page at the next crawl. `RunOffer` therefore adds an offer to the result only when it went through; any exception (a transient failure, a failed search page, a failed detail call) drops everything of the offer, urls included, and becomes a `Warning` plus a logged error, the next offer goes on. Only the caller's cancellation is rethrown, and a cancelled crawl delivers nothing. A permanently missing single item (a 404 detail call) may be skipped with a warning instead. Known urls: `Configure(Func<CancellationToken, Task<IEnumerable<string>>>)` is asked once per crawl, becomes one read-only `HashSet` shared by all crawlers (nothing writes to it), each crawler adds what its finished offers found (`IsKnown(url, offer)` looks in all three).

**Wallpaper settings and availability** — `AddWallCrawler(s => ...)` builds `WallCrawlerSettings` and registers it as singleton. A crawler that needs configuration overrides `IsAvailable`; `WallCrawlerProvider` leaves unavailable ones out, so they vanish from sites and categories (and a consumer like aemarcoInternals then drops their crawl rows as obsolete).

**Wallhaven** — through the api (https://wallhaven.cc/help/api), available only with `WallhavenApiKey` (sent as `X-API-Key`); the html crawler is retired in `Crawlers/Obsolete/`, the friendly name stays `Wallhaven`. The api lives apart from the crawler: `Contracts/Clients/IWallhavenClient`, `Clients/WallhavenClient.cs` (its `AddWallhavenClient()` registration, the typed `HttpClient` with base address, user agent `aemarcoWallpaperCrawler` and key, and the request pipeline) and `Model/Clients/WallhavenModels.cs` (json shapes); the crawler only knows the interface. The client goes through the shared crawler request pipeline (`AddCrawlerPipeline()`: retries on timeouts, 429 and 5xx, then rate limiting), `wallhaven.cc` at 40 calls/min, evenly, without jitter (api limit 45). Per page one search call, and a `/w/{id}` call for the tags of new walls only (`IsKnown`). `path` is the same `w.wallhaven.cc/full/...` url the html crawler stored, so known-url dedup carries over. With a key the api applies the account's browsing settings (AI art filter, tag blacklist); the website's `ai_art_filter` url parameter has no effect on the api (checked), so the account decides. Offers: General/Anime/People × SFW/Sketchy/NSFW; General maps to `Category.None` ("no category known"), which a consumer has to map to its default category itself (aemarcoInternals matches the category string, its default has an empty one). Offline tests serve saved real api responses (`Tests/.../Resources/TestData/Wallhaven`); the live tests include Wallhaven only when `WALLHAVEN_APIKEY` is set in the environment.

**Country resolution** — `CountryService` (in core, backed by embedded `CountryRegionData.json`) matches whole words, longest name first; keep that invariant (a past bug matched "Oman" inside "Romania").

## Testing

- Test output goes through `.Dump()` from `aemarcoToolboxTesting` (System.Text.Json, so it cannot serialize an `Exception`: dump its message instead). `TestOutput.NothingExpected` (`PersonTests/_TestStuff`) warns when a site delivers a value the sample does not expect.
- Tests that hit the **live sites** carry `[Category("LiveSite")]` (set on `PersonInfoTestsBase`, `PersonNameInfoCrawlerBase` and `WallpaperCrawlerTests`; the string matches the filter in `build/Build.cs`). The Nuke `Tests` target filters them out on a server build, because sites block or reset calls from GitHub's datacenter IPs; locally everything runs. A new live-site test class needs the category too. `WallpaperCrawlerTests` builds its cases from the live offers, so its discovery still calls sites even when filtered.
- Person crawler tests hit the **live sites**. Per-site tests inherit `PersonInfoTestsBase<TCrawler>` (`Tests/aemarco.Crawler.PersonTests/_TestStuff`) and declare `Expected*` properties for one sample person; a null expectation just prints the actual value instead of asserting. `[SkipTesting]` on a crawler class makes its tests no-op. Failures are often site changes, not code bugs.
- Tests resolve crawlers via `IocHelper` using the real `AddPersonCrawler()` registration with `NullLogger`.
- No waits in tests: the crawler rate limiting paces the live sites. That holds only with one shared provider per test project (one `CrawlerRateLimiter`), so `IocHelper` hands out a shared container for plain resolves (a fresh one only with `beforeResolve`) and `WallpaperCrawlerTests` resolves from a static provider. A new live test resolves from those, never from its own `BuildServiceProvider()`.
- `InternalsVisibleTo` for `<Project>Tests` is wired in `Directory.Build.props`, so tests can use internal types.
